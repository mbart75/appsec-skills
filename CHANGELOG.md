# Changelog

## Unreleased

- **`appsec-review`: the reviewing agent keeps secret values out of what it reads.** In run 3 of the 0.7.7 regression check, the agent printed the history of `.env.production` with `git log -p` through its own `sed` filter, which missed one value: the bench's fake database password went into its context, and so to the model provider. `SKILL.md` now asks the agent to locate secrets with the redacted scanner outputs and with commits, paths and line numbers. A new recipe in `references/secrets-supply-chain.md` gives the commands for the facts a review needs without the value: which commits touched a secret file, which variables it held, a value's prefix and length, a JWT's claims. It also says how to keep a scanner's output masked when it is run by hand. Whether an agent follows the rule cannot be tested deterministically; the commands themselves can. New test `tests/secret-recipes.sh`, in CI, runs the published commands on the bench's blind copy and checks that each prints what it promises and none of the seeded secrets. A control proves the check catches a raw `git log -p`. Changing a published command to print the file makes the test fail.
- **`run-scanners.sh`: PSScriptAnalyzer leaves a file when it finds nothing.** The summary said `ran`, but no `psscriptanalyzer.json` was written, and a reviewer re-ran it by hand. The output is now always a JSON array, `[]` for a clean scan. `tests/run-scanners-psscriptanalyzer.sh` gains a clean repository: that check fails on 0.7.7 and passes now.
- **`run-scanners.sh`: Trivy is listed when it is missing.** On a repository with IaC or container files, an absent Trivy left no line in the summary, while every other absent scanner is listed `MISSING` with its install command. It now shows `trivy MISSING install: brew install trivy | https://github.com/aquasecurity/trivy`. `tests/run-scanners-checkov.sh`, which runs with only Checkov on the PATH, checks it: 2 of 16 checks fail on `main` at `a34db16`, 16/16 now. The bench was not run again: this only adds a summary line.
- Installer header comments say what the installers do: inside a skills folder, only `appsec-*` folders are created, replaced or removed, and installing also creates the chosen skills folder (and its parents) when it is missing, as the README says since 0.7.6; uninstalling never creates it. Checked with `install.sh` and `install.ps1` on throwaway folders. Comments only.
- **Bench v1 key: 42 → 43 flaws.** V43: the upload folder sits inside the application tree, which `scripts/deploy.sh` empties on every deployment, so each deployment erases the users' files. Found by the review of `secure-app` in the 0.7.7 regression check, where it had been left unfixed; the same defect is in `vulnerable-app`. `secure-app` now keeps uploads outside the deployed tree (`UPLOAD_DIR`, default `/var/lib/tinyshop/uploads`, in the API and the worker). `check-key.py`: 43 flaws, 0 problems. Earlier scores are out of 42 (or 38 before 2026-10-24) and are not rescored. The bench was not run again.

## 0.7.5 (2026-10-24)

Security fixes, same family as 0.7.4: the reviewed repository must not configure the scanners that review it.

- **`run-scanners.sh`: Checkov no longer reads the reviewed repository's configuration.** Checkov loaded a `.checkov.yaml` or `.checkov.yml` from the scanned repository (and from the folder it was run in), and that file can load Python checks and skip findings. Checkov now scans a copy without these files, from an empty folder, so the configuration of the reviewed repository has no effect and nothing it contains is imported. Reported paths still name the repository. The files found are listed in `checkov-repo-settings.txt` and flagged `IGNORED` in the summary, as for gitleaks. Inline `#checkov:skip` comments cannot be turned off: they are listed there too (`checkov skips LISTED`), and `SKILL.md` asks the reviewer to name them and look at what they hide. Removing either the copy or the empty working folder makes it fail again.
- **`run-scanners.sh`: the reviewed repository could hide its secrets from TruffleHog** (Medium). TruffleHog drops any finding whose line carries a `trufflehog:ignore` comment, so a reviewed repository could hide a secret in its files or its history with one comment. In addition, `PRE_COMMIT=1`, `HUSKY=1`, `HUSKY_GIT_PARAMS` or `TRUFFLEHOG_PRE_COMMIT=1` in the environment switch `trufflehog git` to pre-commit mode: it scans `HEAD..HEAD` (nothing), keeps verified results only and trusts the repository's git config, so the history scan reported nothing. TruffleHog now runs with `--no-ignore-tag` and without those variables. The comments and the variables found are listed in `trufflehog-repo-settings.txt` and flagged `IGNORED` in the summary, as for gitleaks. `--no-ignore-tag` exists since TruffleHog 3.97.5: older versions still run, and the summary says `trufflehog OUTDATED` (they obey the comments).
- **`run-scanners.sh`: TruffleHog and Bandit outputs kept the secrets in clear** (Medium). TruffleHog's JSON holds the secret in `Raw`, `RawV2` and `SecretParts`; Bandit's holds the flagged lines in `code` and a hardcoded password's value in its message. The output folder is meant to be outside the repository, but it is still a file of live secrets left on disk, next to a report that must redact them. Neither tool can redact its own JSON, so both now go through `scripts/redact-findings.py` (standard library) before anything is written: those fields become `[REDACTED]`, the values found in them are removed from every other field, and file, line, commit and detector stay. Input that cannot be parsed is dropped, not copied. Without `python3`, TruffleHog and Bandit are reported `NOT RUN` rather than writing secrets. gitleaks already ran with `--redact`. On `bench/vulnerable-app`, `trufflehog.json` held the bench's seeded database password; it no longer does.
- New test `tests/run-scanners-secrets.sh`, run in CI with TruffleHog 3.99.2 (checksum pinned) and Bandit 1.9.4 (nothing published in the last 7 days): a throwaway repository hides secrets with `trufflehog:ignore` in its files and history, and the scan runs once plainly and once with the four variables set; every file written must be free of the fake secret values, whatever scanners are installed. What the skills changed:

- **Threat model**: without the skill, the analysis was good but stayed in the chat. What this shows, plainly:

- **Detection**: the model alone already found all eight real flaws. The first version of the skill did *worse* (3.5 out of 6): its anti-false-positive rules pushed the agent to under-report latent or library-level flaws and to under-rate control bypasses, and its SSRF guidance accepted a validate-then-resolve-again guard. Three rules were added from these failures (attack every existing control; exported APIs are entry points; a control bypass is at least Medium) and the SSRF checklist was completed. The current version is level with the model alone, not better. R08 was found after its reference was updated following the miss on that same case, so that result may be partly fitted to the bench.
- **Fixed commits**: no expected flaw was reported again on the seven fixed commits reviewed. On several, the review reported something else in the same area (an unfixed sibling, residual weaknesses around the fix). Rechecked on each project's current main branch three days later: two had since been fixed upstream, one is a documented design choice, and one remains and is handled by coordinated disclosure (not described here). The first check of one of them was wrong, because a single matching line was read without its context: verifying a finding means reading the surrounding code.
- **What the skill adds** is therefore not more detection on these cases but the report itself (work order, verified findings, "Done when", statuses, verify mode), consistent redaction and scope discipline. A baseline without the skill on the fixed commits was not run, so finding residual issues there cannot be credited to the skill.

The v1 bench is easy for current models: both baselines found nearly every textbook flaw. It measures report quality and discipline more than detection. A harder bench (subtle flaws diluted in mostly correct code) is planned.
