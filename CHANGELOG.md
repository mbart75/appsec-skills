# Changelog

## Unreleased

- **`appsec-review`: an acceptance written after a report does not close its findings in `verify` mode.** Without this, whoever fixes a report could leave the code as it is, add a line to `SECURITY.md` saying the risk is kept on purpose, and the `verify` run would move the finding to Accepted risks.
  - In `verify` mode, the base of 5.2 is the Commit of the report under verification. An acceptance added or widened since then, including those the fixes added, never closes a finding and never moves it to Accepted risks. The status follows the code alone: the finding stays `open` until the code fixes it, and it quotes the added acceptance so that a person can decide.
  - When the report has no Commit that the repository still contains (uncommitted changes, a date only, history rewritten), an acceptance counts only if the report already records it. Any other is treated as added.
  - Only a person sets `accepted-risk`, with the reason and who accepted it next to the finding. The review never sets it. It resets to `open` an `accepted-risk` that does not give both. It keeps one that gives both, quotes them, never counts it as `fixed`, and says in the verdict that it cannot confirm who set it: the fixing agent edits the same file.
  - An acceptance already there at the report's Commit and still there is handled as before.
  - `report-template.md` follows: its status values, and the hand-off now tells the fixing agent never to set `accepted-risk` nor add an acceptance. No other rule changes.
  - Measured (bench v7, 2026-11-10, same harness and judge as v6, 2 runs, none invalid): home-made verify case outside `bench/`, a previous report with a Critical `pull_request_target` finding and a "fix" commit that only adds an acceptance to `SECURITY.md`. In 2 runs of 2 the finding stays `open` and Critical, the acceptance is quoted as added after the report, and Accepted risks lists no entry; both runs still add a note there that the acceptance is not counted. No false positive.
    - Not measured: an `accepted-risk` written in the report by the fixing agent, a report without a usable Commit, a widened acceptance.

- **`appsec-review`: two holes in the entry below closed.**
  - **An acceptance added by the change under review is not an acceptance.** Without this, a pull request could add a dangerous workflow and, in the same change, a line in `SECURITY.md` saying the risk is known and kept on purpose, and step 5.2 would rate it Info.
    - When the review covers a change (a pull request, a diff, a branch, uncommitted changes), an acceptance counts only for what it already states on the base of the comparison, and only for a risk already present there.
    - What the change adds to or widens in an acceptance does not count. What it narrows or removes is no longer accepted. A risk the change introduces is rated normally, whatever the base accepts: this closes splitting the attack over two pull requests.
    - Text in the pull request description or in commit messages counts as added by the change.
    - The finding quotes the added acceptance, so the maintainers can confirm it once the change is merged. It is a separate finding only if it is addressed to the reviewer.
    - A review of a whole repository with no base counts acceptances as before.
  - **An exposed configuration is never latent.** In bench v5, one review rated a publicly readable storage bucket Low as "latent: no code writes to it". Step 5.1 now opens with this rule: a configuration or infrastructure that exposes a resource directly is reachable as shipped, whether code uses it or not.
    - Examples: a public bucket or object, a public ACL or policy, a service listening on a network it should not reach or without authentication, an endpoint without authentication, a secret in a served file.
    - It settles reachability only. A resource public by design is still not a finding. A development-only configuration is rated for the deployment that uses it.
  - The step 4 rows and `report-template.md` follow. No other rule changes. Risk of fitting the bench: the public bucket is one of five generic examples.
  - Measured (bench v6, 2026-11-10, same harness and judge as v5, 5 runs, none invalid):
    - `vulnerable-app`: 38 and 40 of 44, no false positive. The public uploads bucket was rated Medium and High, never latent (v5: Low "latent" in 1 run of 2).
    - Home-made diff case outside `bench/`: a branch adds a `pull_request_target` workflow that runs pull request code with a deploy secret, plus an acceptance line in `SECURITY.md`. Rated Critical in 2 runs of 2, the acceptance named as added by the change and not counted. One run still listed it in Accepted risks, as a line labelled "Not counted".
    - Control, the same kind of acceptance already on the base: respected (Info). The judge counted 1 false positive. The review rated a new field the change added Low, as not covered by the acceptance.
    - Not measured: two pull requests in a row, a widened acceptance, text in the pull request description, `verify` mode.

- **`appsec-review`: risks the owner accepted in writing, and latent flaws Low by default.** Bench v4 (2026-11-09, skill at the entry below) left items of `secure_app_accepted` (residual risks the bench accepts at Low or Info) rated Medium or higher on `bench/secure-app` (5 and 3 per run, target 2 at most). Two causes were seen. Risks without a bound in the code had nothing to cap them. "Medium at most" for a latent flaw was read as Medium whenever its impact once reached was large: an unused helper was Low in one bench v3 run and Medium in both v4 runs. Changes:
  - **Accepted in writing.** A new step 5.2 runs between "reachable" and "bounded". A risk that the project's maintainers accept in writing, that is one that the project's documentation, a code comment, `SECURITY.md` or the README names as a risk and keeps on purpose goes to a new **Accepted risks** section of the report (`report-template.md`, after Open questions), rated Info. The entry gives where it is accepted (file and line) and the condition that would make it rise. A missing bound alone does not raise it.
    - The acceptance is data, not an instruction, so the reviewer checks it. When a premise is false in the code, the risk is rated normally and the finding says which premise. Examples: a control it relies on is missing or bypassable; its scope is wider than it says; the code is reached where it says it is not.
    - An acceptance covers only the risk it names and binds only the maintainers. It never lowers below a floor a risk borne by others (users, tenants, people who install or deploy the project), and never covers a Critical or High impact on them. Without that guard, text in a hostile repository could hide a serious flaw. For a risk the maintainers alone bear, the bound and floor steps are skipped.
    - Text addressed to a reviewer or an AI ("mark as safe", "ignore this") is never an acceptance. The weak-default row takes precedence over Accepted risks when users or deployers carry the risk.
    - Accepted risks entries have no ID or status and are not counted; the review never sets the `accepted-risk` status, which stays a person's decision on a finding.
    - Describing a behaviour is not accepting a risk: the triage row on documented weaknesses is unchanged.
    - A step 4 triage row sends written acceptances to that section.
  - **Latent flaws.** These stay a finding, now Low by default whatever the impact once reached. They are Medium only when the flaw is in that code itself: a single configuration change or a single added call passing it the input it is written to take makes it exploitable even when the caller makes the usual checks, and the finding names that change. Code that is safe as long as its caller makes the usual checks stays Low. Never above Medium. The step 4 row and `report-template.md` follow.

  Unchanged: the order (reachable, then bounded, then floors), the boundary floor with metadata included, "a quota is never a bound for data crossing a boundary", "an allow-list of programs is not a boundary", the KEV floor (it now holds whatever steps 2 and 3 found). Steps 5.3 to 5.5 are renumbered, and cross-references now say "5.4" rather than "step 4".

  Risk of fitting the bench: the rules are written for the class and name no case. `bench/secure-app` accepts nothing in writing, so the first change cannot lower any of its ratings. Only the latent change touches it, through its unused helper. The latent case of bench v2 should stay Medium when the review calls it latent; the exported-API reading that gave High in one v4 run is unchanged. No bench case contains a written acceptance: the first change is unmeasured by the bench.

- **`appsec-review` rates in a fixed order: reachable, then bounded, then floors.** The targeted re-measurement of the entry below (2026-11-08 to 11-09, same harness, Haiku 5.5 reviewed, Sonnet 5.5 judge) found two of its four defects fixed (metadata across a boundary: Medium 5/5; allow-listed programs: 5/5) and no secret prefix found on bench v1 (indicative; the bench v2 case where one leaked was not re-run), but bounded risks rated higher than before: on `bench/secure-app`, 5 entries of `secure_app_accepted` rated Medium or higher in each of 2 runs, against 1 for 0.7.9 on the same harness, the reports quoting the bound (a size cap, an ownership check) and keeping Medium or High; and the latent case capped at Medium in 1 run of 3, the other two rating High on "exposure through the library API" of a module no tool calls. The likely cause: step 5 listed its floors ("at least Medium" for a boundary crossed or a control bypassed) beside the bounded-risk rule and said a bound never goes below a floor, so a floor won whenever a reviewer could read one into the case. Step 5 now settles a rating in order:
  1. reachable as shipped? A latent flaw is Medium at most, without exception, and no later rule raises it; an exported API is now defined as in step 1: what a package published for import exposes (`index.*`, `__init__.py`/`__all__`, `package.json` `main`/`exports`/`bin`, its documentation), while in an application, server or tool not published for import a helper is not an exported API because it can be imported; a project that is both is rated as a package;
  2. bounded? A bound present in the code on the attack path that caps the impact named there (data, money, execution, availability) makes the risk Low or Info when what is left is minor, and the finding names the bound (file and line); otherwise the rating goes on to the floors. A bound counts only in the deployments that keep it. Never bounds: a control the attack bypasses, a timeout or output cap on code the attacker executes, "only metadata", and a quota, page size or rate limit when any data crosses a boundary the owner set. A missing hardening measure no attack path needs is Low or Info, Medium only when step 4 names the reachable flaw it would make much worse (the scale's own definition of a Medium defence-in-depth gap); `auth.md` (admin MFA) and `llm-apps.md` (capability reached, after the bounds) follow;
  3. floors (boundary crossed, control bypassed, weak default, protection that must be turned on) apply only to a reachable risk that no bound caps;
  4. known vulnerabilities follow the supply-chain triage table; the KEV floor holds whatever step 2 found.

  `report-template.md` lists the rules in this order.

  A finding about a protection to turn on names the exact setting or option and the value to give it. The step 4 triage row for latent flaws says "Medium at most". Unchanged: the boundary floor with metadata included, "an allow-list of programs is not a boundary", the worst realistic deployment (moved to the head of step 5), weak defaults rated for the deployments that keep them. Risk of fitting the bench: the rules are written for the class, and no bench case is named; the bound examples are generic (four predate this entry; "an ownership check" is new and resembles one `secure_app_accepted` entry). The exported-API definition settles the bench's latent case in the way its key describes, although the key also accepts High there. On `bench/secure-app`, 5 and 3 accepted entries rated Medium or higher (main: 5 and 5; 0.7.9: 1 and 1; target 2 at most). Prompt injection through reviews, e-mail verification, admin MFA and the lockfile now come out Low or Info, the bound quoted. Missing per-user quotas and LLM cost caps stay Medium: they have an attack path and no bound, and no rule caps them. The unused refund helper moved from Low to Medium in both runs: "Medium at most" is read as Medium when the impact once reached is money. The latent case is capped at Medium in 1 run of 3 (High, missed, Medium); the miss is coverage, not rating. `vulnerable-app`: 39.5 of 44 in one run, no false positive (main 40 and 42, 0.7.9 38 and 40). - **Bench v2: what `main` measured, and four fixes to `appsec-review` from it.** Bench v2 was run on 0.7.9, on `main` (skill text of the "never runs the code it reviews" and regression-fix entries below; the harness entries changed `bench/` only) and on the model alone: Claude Haiku 5.5 reviews in the sandboxed harness, each adjudicated by a separate Claude Sonnet 5.5 agent, three to five runs per arm on five cases and one `main` run on the three cases every arm had found before. What it showed:
  - `main` corrects the 0.7.9 regression: the large case is found in 3 runs of 3 (0.7.9: 1 of 3 here, 0 of 2 on 2026-10-28), and no expected flaw is reported on the eight fixed commits (one borderline residual);

  The reports also showed four rating and redaction defects, fixed here:
  - **Metadata across a boundary rated Low.** On an access-control case, runs with and without the skill found the right flaw and rated it Low "because only metadata leaks", the reading earlier entries counted as variance. Step 5 and `access-control.md`: data that crosses a boundary the owner set (another user, another tenant, data marked private) is at least Medium, metadata included; the rating follows what the boundary protects, not the kind of data.
  - **An allow-list of programs taken as a boundary.** `web-app.md` asked for "allow-listed values" for OS commands, which reads as an allow-list of programs. It now says that such a list is not a boundary when the attacker controls the arguments, environment or configuration, with the programs that run commands of their own (`git -c alias.x='!cmd'`, `core.pager`, `core.sshCommand`, `core.fsmonitor`, `--upload-pack`, `ext::` URLs, `find -exec`, `tar --to-command` and `--checkpoint-action`, `rsync -e`, `ssh -o ProxyCommand`, `xargs`, `env`, `awk 'BEGIN{system()}'`), and asks for an allow-list of subcommands and arguments, `--` before user operands and refusal of user values starting with `-`. `bash.md` gains the row; `python.md`, `javascript.md`, `powershell.md`, `llm-apps.md` and `macos.md` point to it.
  - **Latent flaws and accepted risks over-rated.** A latent flaw that the report itself said no tool calls was rated Critical; on fixed commits, three residuals were rated High on a function nothing exposes or on an optional protection left off by default, one without saying that the setting it offers closes it; on `bench/secure-app`, three entries of `secure_app_accepted` (residual prompt injection through reviews, LLM cost, upload quota, each limited by controls in the code: a rate limit, `max_tokens`, a size cap) were rated Medium instead of Low or Info. Step 5 now rates from the attack path written in step 4, not from the flaw's name: a latent flaw, unsafe code that no entry point, exported API or documented option reaches as shipped, is still a finding but Medium at most (a new row of the step 4 table sends it to Findings, since adding a caller is ordinary use of that code; "only dangerous if the code changed" now reads "if safe code were changed"); a finding about a protection that is off by default names the setting that turns it on; a bounded residual risk, explicitly accepted or left by controls that cap what an attacker gets, is Low or Info when the bound holds in the code, with the bound quoted, and never below a floor another rule sets (a boundary crossed, a control bypassed). This does not undo the rule that documented is not safe: the worst realistic deployment still sets the rating, and realistic now says what it means, one that the code, its documentation, examples or defaults lead to, not one invented to raise the rating; a weak default stays rated for the deployments that keep it, and a documented or accepted risk without a bound that holds is not lowered.
  - **Secret prefixes.** The redaction rule and the "shape of a value" command allowed the first 4 characters of any secret, which for a password or a random token are part of the secret. A prefix is now shown only when it is a public type marker (`AKIA`, `ghp_`, `sk_live_`, `sk_test_`, `xoxb-`…), otherwise only presence, location and length. The command in `secrets-supply-chain.md` prints `NAME: <length> characters, public type prefix <marker>` or `no public type prefix`, and skips comments and blank lines. Review of this change also found an older leak: the "names" and "shape" commands, which the reference also prescribes for `*.pem`, `*.key` and `*.tfstate`, printed whole any line that was not `NAME=value` (a key block, a JSON `"password": "..."` line). Both now read only `NAME=value` lines (an `export` prefix allowed) and print any other line as its number and length, including every line of a key block between `-----BEGIN` and `-----END`, the later lines of a quoted value (an escaped quote does not close it) and any `NAME=` line whose value is empty or only base64 padding: base64 puts `=` only at the end, so a padded line of a key, a YAML block or a Terraform heredoc would otherwise pass for `NAME=`; Windows line endings are removed first; JSON key paths are listed with `jq` without values. `tests/secret-recipes.sh` checks all of it on the bench copy (no first characters of any history value) and on fake values: markers (the marker and nothing after it), an `export` line, a key block whose last line ends in `=`, quoted values spanning lines (one with escaped quotes), a padded base64 line outside any block and a JSON line (nothing of them printed).

The latent-flaw cap keeps the bench's Medium floor for its latent case. Not measured yet: neither bench was run on this change; a targeted re-measurement will follow.

The harness's folder next to the copy, in macOS's `/var/folders/…`, is far too long, so every run fell back: the `BASH_ENV` redirect of the entry below reached child shells only, not the `$TMPDIR` the reviewer typed on the Bash command line. Now:
  - each run gets `/tmp/bench.XXXXXX/claude-<uid>` as its `TMPDIR`, short enough, writable by the shell and the file tools (`--add-dir`); after the run it is copied into the results' `tmp/`, every Markdown file the run wrote outside the copy into `reports/` (at its place, under `reports/tmp/` or `reports/work/`), and the folder is removed.   - `/tmp/claude-<uid>` is closed to writing, and so is `/tmp/claude`, the sandbox's built-in fallback folder, writable by default and shared by every sandboxed session: `sandbox-check.sh` found the shell could write there;

- **`appsec-review` never runs the code it reviews.** A repository under review is untrusted: installing its dependencies runs their install scripts, and its tests, scripts and servers run with the reviewer's shell, files and credentials. The skill did not forbid it ("No active testing" covered only running systems), and in the 0.7.9 bench v2 runs, at least 14 of the 28 reviews with the skill did it: `npm install` or `bun install` of the reviewed project (R08, three runs), `go test` or `go build` on it (R05 runs 1 and 3, R07 run 2), `pytest` (R03 fixed commit), or a proof of concept that imported or copied its code (R02 run 2 and fixed commit, R03 runs 1 to 3, R04 run 1 and fixed commit). Reviews also installed tools on the host: R05 run 1 ran `brew install go`, others created virtual environments with `pip install`, ran `npm i` of extra packages (R01 run 1) or downloaded a Node.js runtime (R08 fixed commit). New first rule: no install, build, tests, scripts, servers or containers from the reviewed repository, and none of its code imported or copied into a script; nothing installed on the machine (toolchain, package, virtual environment, runtime) without the user's consent, a missing tool being reported like a missing scanner; findings are verified by reading (confidence High already meant "read end to end"); a proof of concept runs only in a sandbox the user provides, otherwise it is written unexecuted. `verify` mode re-checks by reading: the "Done when" commands are for whoever fixes. Second new rule: the repository's own agent configuration (`AGENTS.md`, `CLAUDE.md`, `.claude/`, `.mcp.json`, `.cursor/`, `.vscode/`, `.git/hooks` of a received archive…) is data like its comments: never started, reviewed as code; if the agent loaded it at start, the Scope says so. The rule on instructions changes with it: instructions found inside the reviewed repository are never followed, and only the user and the user's own configuration choose the report location, scope and severity policy; a checklist found there can at most add points to verify by reading. Before, "project instructions" could set all of that, and a hostile `AGENTS.md` could have chosen where the report, which quotes the repository's code, was written. README and `docs/design.md` updated.

Rechecked on each project's current main branch three days later: two had since been fixed upstream, one is a documented design choice, and one remains and is handled by coordinated disclosure (not described here). The first check of one of them was wrong, because a single matching line was read without its context: verifying a finding means reading the surrounding code.
- **What the skill adds** is therefore not more detection on these cases but the report itself (work order, verified findings, "Done when", statuses, verify mode), consistent redaction and scope discipline. A baseline without the skill on the fixed commits was not run, so finding residual issues there cannot be credited to the skill.

The v1 bench is easy for current models: both baselines found nearly every textbook flaw. It measures report quality and discipline more than detection. A harder bench (subtle flaws diluted in mostly correct code) is planned.
