# Supabase row-level security: what to verify in the policies

When the browser talks to Supabase directly, the policies are the whole access control. This checklist is for reading them: from the SQL migrations in the repository (`supabase/migrations/`), or from an export the owner runs in the SQL editor. The basics shared with other back ends (`service_role` in the browser, RLS enabled with no policy, `using (true)`) are in `access-control.md`; to confirm a reading on a running system, use `supabase-rls-probes.md`; to fix the findings, hand the report to `appsec-harden`.

Each item has the read-only query that answers it. Replace `public` if the API exposes other schemas.

## Checklist

| # | Check | What a flaw looks like | Verify |
|---|---|---|---|
| 1 | RLS enabled on every exposed table | A table created by hand or by a migration without `enable row level security`: readable and writable by anyone with the public key | `select tablename, rowsecurity from pg_tables where schemaname = 'public';` every row `true` |
| 2 | Ownership on reads and writes | A `select`, `update` or `delete` policy that does not compare the owner column to `auth.uid()`, or compares it to a value the client sends | `select tablename, policyname, cmd, roles, qual, with_check from pg_policies where schemaname = 'public' order by tablename, cmd;` each `qual` ties the row to `auth.uid()`, or to a membership row the user cannot create alone (item 4) |
| 3 | `with check` pins the owner on insert and update | An `insert` policy whose `with_check` does not compare the owner column to `auth.uid()`; an `update` policy with an explicit `with check (true)`, which lets a user move a row to another owner | Same query: every `insert` and `update` row has a `with_check` on the owner column. An `update` policy with no `with check` reuses its `using`, which is fine |
| 4 | Upserts have both sides | The client writes with `upsert` (`insert ... on conflict do update`): it needs an `insert` and an `update` policy, both pinning the owner. One strict policy and one loose policy leave the loose path open | List the policies of every table the client upserts into; both commands present, both pinned |
| 5 | Permissive policies add up | Two permissive policies on the same table and command are combined with OR: one wide policy cancels a strict one | Same query, grouped by table and `cmd`: read every permissive policy, not only the one with the expected name |
| 6 | Privileged columns not writable by the user | RLS filters rows, not columns: an owner who may update their profile can also set `role`, `status`, `plan`, `is_verified` on it | `select grantee, column_name, privilege_type from information_schema.column_privileges where table_schema = 'public' and table_name = '<table>';` no `UPDATE` (or `INSERT`) by `authenticated` or `anon` on those columns; or a `before update` trigger that rejects the change (`select tgname, pg_get_triggerdef(oid) from pg_trigger where tgrelid = 'public.<table>'::regclass and not tgisinternal;`) |
| 7 | No authorization on user-editable claims | A policy reads a role from `auth.jwt() -> 'user_metadata'` or `raw_user_meta_data`: the user can change those values themselves | Search `qual` and `with_check` for `user_metadata`. Roles come from a table the user cannot write, or from `app_metadata` set server-side |
| 8 | Relation rows created by the right party | A row that grants access (membership, sharing, follow-up, invitation accepted) can be inserted by the party who gains access: anyone grants themselves access to anyone | The `insert` policy on the relation table checks `auth.uid()` against the party who gives access (the data owner), or inserts only happen through a function that checks an invitation; the column that activates the relation (`status`) can only be set by that party |
| 9 | `security definer` functions | A function exposed through `/rpc` that runs with its owner's rights: it bypasses RLS, so its own checks are the access control | `select p.proname, p.prosecdef, p.proconfig, pg_get_function_identity_arguments(p.oid) from pg_proc p join pg_namespace n on n.oid = p.pronamespace where n.nspname = 'public' and p.prosecdef;` each one has a fixed `search_path` in `proconfig` (`search_path=""` with schema-qualified names, or `pg_catalog, public`), takes the caller's identity from `auth.uid()` and never from a parameter, returns only the columns the caller needs, and is not executable by `anon` unless intended (`select grantee, privilege_type from information_schema.routine_privileges where routine_name = '<function>';`) |
| 10 | Views do not bypass RLS | A view in an exposed schema runs with its owner's rights by default and returns every row | `select c.relname, c.reloptions from pg_class c join pg_namespace n on n.oid = c.relnamespace where n.nspname = 'public' and c.relkind = 'v';` each view has `security_invoker=true` (Postgres 15+), or is not exposed |
| 11 | Second factor for sensitive roles | Staff, admins or professionals who see other people's data reach it with a password alone | A `restrictive` policy on the sensitive tables requires `(select auth.jwt() ->> 'aal') = 'aal2'` for those roles; MFA enrolment exists in the app |
| 12 | Size and shape of JSON and text columns | Clients write whole JSON objects or free text with no limit: storage abuse, slow pages, forged fields shown to other users | `select conrelid::regclass, conname, pg_get_constraintdef(oid) from pg_constraint where contype = 'c' and connamespace = 'public'::regnamespace;` a check such as `octet_length(data::text) < 100000` on each client-written `json`, `jsonb` or long `text` column, and `jsonb_typeof` or a schema check where the shape matters |

## Reporting

- A gap is a finding only once the request an attacker sends is written: "as a signed-in user, `POST /rest/v1/<table>` with `<owner column>` set to another user's id is accepted (insert policy has no `with check`)". Rate it with `access-control.md`: another user's personal data is High, every user's data or a role change to admin is Critical.
- A policy you could not see (no migrations, no export) is an open question, with the query above that would decide it.
- Quote the policy or the query output you relied on in the finding's evidence.
